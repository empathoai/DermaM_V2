## 2026-08-19 — graphify scoped to `src/` only, output at project root
**Decision:** Built the graphify knowledge graph from `src/` (code only), with `--out .` so `graphify-out/` lives at the project root, not nested under `src/`.
**Why:** Running `graphify extract .` over the whole repo pulled in 64 docs + 153 images and failed without an LLM API key (semantic extraction needed for non-code files). Scoping to `src/` with `--no-cluster` avoids that entirely since a code-only corpus needs no key. The skill's own instructions (`CLAUDE.md` → `## graphify`) assume `graphify-out/` at the project root, so `--out .` was needed to match that convention.
**How to apply:** Re-run `graphify update .` (not `extract`) after code changes — no API cost. Only re-run a full `extract` if the graph needs docs/images included, and only then decide whether to supply an LLM backend key.

## 2026-08-19 — `ai-visibility-checker`'s "never simulate an AI engine response" rule kept even though the user asked for non-blocking heuristic mode everywhere

## 2026-08-20 — `Picture.jsx`'s `<picture>` element forced to `display: contents` rather than styling it with the consumer's className
**Decision:** Fixed the FeaturedServices image-gap bug (see `PROGRESS.md`) by adding `style={{ display: 'contents' }}` to the `<picture>` wrapper inside `src/components/shared/Picture/Picture.jsx`, instead of also passing `className`/`style` down onto `<picture>` itself (e.g. `<picture className={className}>`).
**Why:** `display: contents` removes `<picture>` from the box-generation tree entirely, so the `<img>` becomes the effective flex/grid child of whatever the consumer's container is — this exactly reproduces the pre-migration markup (a bare `<img>` with no wrapper) that every consumer's existing CSS (`FeaturedServices.module.css`, `AboutPage.module.css`, `MediaBlock.module.css`, etc.) was already written for. Passing `className` to `<picture>` instead would have required every consumer's CSS to be checked/duplicated for two class targets (`<picture>` and `<img>`) and could have caused double-styling bugs (e.g. two elements both getting `width:100%; height:100%` in nested boxes with different box models). `display:contents` is a single, universal, zero-config fix that doesn't require touching any of the 7 consumers.
**How to apply:** Keep `Picture.jsx`'s `<picture>` wrapper as `display:contents` — don't remove it or start passing sizing props to `<picture>` directly. If a future browser-compat concern rules out `display:contents` (rare — it's been supported in all evergreen browsers for years), the fallback is to move `className`/`style` onto `<picture>` AND audit every consumer's CSS for the two-element case, not a quick patch.

## 2026-08-20 — SEO backlog item 5.4 closed without implementing: font `preconnect`/`preload`/`font-display` deferred
**Decision:** Did not add `<link rel="preconnect">` for Google Fonts, nor move the `Poppins` load from CSS `@import` to a `<link>` in `index.html`. Closed 5.4 as "no se implementa por ahora" instead of leaving it open indefinitely.
**Why:** Ran a 5-advisor council (Contrarian, First Principles, Expansionist, Outsider, Executor) plus peer review on whether to make this change. Key finding: `&display=swap` is already present in the existing `@import`, so the FOIT problem this ticket exists to solve is already solved — the only remaining upside is an unmeasured, likely-millisecond DNS/TLS discovery-latency shave. Weighed against touching `index.html` (a shared, load-order-sensitive file) on a project explicitly frozen for stability with a visual-regression suite that already carries 9 pre-existing unrelated failures (degraded signal-to-noise for catching a new one), the risk/reward didn't clear the bar for a "near-final, protect what works" project. User confirmed: leaving it as-is has no negative impact (no broken FOIT, no measurable SEO penalty) — it's a "nice to have," not a fix for something broken.
**How to apply:** Do not re-open 5.4 speculatively. Revisit only if real performance metrics (Lighthouse/PageSpeed/Core Web Vitals data, not assumption) show font-loading latency is an actual measured problem — then the lowest-risk version to implement is `<link rel="preconnect">` tags added *alongside* the existing `@import` (not replacing it), which the council flagged as capturing most of the benefit with near-zero risk to the CSS cascade or Playwright snapshots. Do not bundle in font self-hosting, subsetting, or `font-display:optional` — those came up during the council as scope-creep tangents, not part of this ticket.
